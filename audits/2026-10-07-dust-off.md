Full audit of the appliance family after five months with little
activity on `main`. Scope: `dev-commons`, `appliance-core`, `lab-kit`,
`lab-router`, `samba-addc-appliance`, `smb-proxy-appliance`,
`smbproxy-session-vfs`. The Wine repositories are out of scope.

It covers four things:

1. What state the code is actually in (it is not what `main` says).
2. Findings, ordered by severity.
3. A redesigned test strategy.
4. A plan for upgrading appliances that are already deployed.

The decisions the owner needs to make are listed at the end.

## HIGH severity

### H1 — `main` is behind production; three PRs have sat unmerged for two months

- **Repos**: `dev-commons`, `samba-addc-appliance`, `smb-proxy-appliance`
- **Evidence**: section 1. The production proxy runs per-tree session
  mounts (`smbproxy-session-mount`, `smbproxy-share-worker`,
  `smbproxy-vfs-version-check`) that exist only on the branch. `main`'s
  `smb-proxy-appliance/AGENTS.md`, `docs/LAB-TESTING.md`,
  `lab/scenarios/backend-mount.sh`, and `tests/unit-helpers.sh` still
  require `nobrl`.
- **Why it matters**: this is the "documentation drifts from reality"
  failure mode that `CONTEXT.md` warns about. A rebuild or a new helper
  working from `main` would undo the locking fix. Every later change
  (remediation sessions, new components) needs one baseline.
- **Recommendation**: make the branches the baseline. Fix M4 on them,
  wire their tests into preflight (M5), have the owner review the PRs,
  merge, and tag (see section 5, Phase 1).
- **Resolution**: fix (owner, 2026-10-08)

### H2 — "Install updates" on the proxy can take legacy shares offline

- **Repos**: `smb-proxy-appliance` (branch), `appliance-core`
- **Evidence**:
  - `smbproxy-sconfig.sh` `run_updates_now` and `prepare-image.sh`
    `action_update` run `apt-get full-upgrade` with no Samba hold.
    `appliance-core/lib/apt-helpers.sh` recommends `full-upgrade` in
    the login banner.
  - Nothing holds or pins `samba` (`grep 'apt-mark hold'` finds
    nothing).
  - In the in-place `0.4.0` install, the VFS is built by hand and the
    expected version is stored in `/usr/lib/smbproxy/samba-version`.
    No package dependency stops apt from moving Samba to 4.22.11,
    which is already in trixie.
  - Samba's upgrade restarts `smbd`. The `ExecStartPre` guard then
    refuses to start it, by design.
  - With the packaged VFS, `full-upgrade` may instead **remove** the
    VFS package to satisfy the upgrade. The result is the same.
- **Why it matters**: following the on-screen advice causes an outage
  of the line-of-business shares. The design intends to fail closed,
  but an operator should never be led there.
- **Recommendation**:
  1. Today, on the production proxy, check `apt-mark showhold`,
     `apt list --upgradable 2>/dev/null | grep -i samba`, and
     `dpkg -l smbproxy-session-vfs`. Then `apt-mark hold` every
     installed Samba binary package until 4.22.11 is qualified.
  2. In code, have the proxy hold the Samba package set whenever a
     legacy share exists.
  3. Make the update menu and login banner say "Samba held at <ver>
     pending qualification" instead of recommending a blind upgrade.
  4. Add a scenario that proves an upgrade attempt leaves `smbd`
     running (T-UPG-2 below).
- **Resolution**: fix (owner, 2026-10-08)

### H3 — The 2026-08-10 review findings are open, including 4 × P1

- **Resolution**: fix (owner, 2026-10-08)

## MEDIUM severity

### M1 — Deployed appliances cannot say which version they run

- **Evidence**: `/etc/appliance-core.provenance` records the
  appliance-core version and commit and `consumer=<repo>`, but not
  the appliance repo's own commit or version. Release names are dates
  (`vYYYY.MM.DD`) with no git tags. In-place updates leave only a
  backup directory as evidence.
- **Why it matters**: an upgrade tool cannot choose a migration path
  without knowing the starting point. Support work starts by guessing.
- **Recommendation**: add `/etc/<appliance>.release`, written by
  `prepare-image.sh` and rewritten by every update. Include the
  appliance version, repo commit, appliance-core version, VFS
  version, Samba package version, and update history. Tag every
  release in git.
- **Resolution**: fix (owner, 2026-10-08)

## 3. Test strategy redesign

The current strategy has two levels: fast static and unit checks on
the build host, then about nine Hyper-V scenarios run by hand. The gap
between them is where H2, M4, and M6 lived. The redesign adds a
container layer in that gap, runs layers L0–L2 in CI, and adds upgrade
testing as a first-class concern.

| Layer | Runs where | Time | What it proves |
| --- | --- | --- | --- |
| L0 static | CI on every push and PR (Linux) | < 1 min | `bash -n`, ShellCheck strict, compliance C01–C12, git file-mode manifest, `git diff --check`, credential grep from `PUBLISH-CHECKLIST.md` §1 |
| L1 unit | CI (Linux), plus a macOS runner (bash 3.2) for Mac-side scripts and a Windows Git Bash runner if Windows stays a dev host | 1–3 min | Every `tests/*.sh` and `tests/*.bats`, discovered automatically |
| L2 container integration | CI in a `debian:trixie` container with **the exact pinned Samba** | 5–15 min | Generated configs pass `testparm`. `samba-tool domain provision` runs headless. VFS builds against the pinned and candidate Samba. Updaters run against sanitized snapshots of each shipped version's `/etc` and `/var/lib` state. The Samba-hold guard (H2) is checked. |
| L3 VM lab | Hyper-V lab through `lab-kit`, run by hand or by a self-hosted runner | 30–60 min | Existing release gate, plus the new scenarios below |
| L4 acceptance | Staging or production maintenance window | owner-run | Real Win2008 SP2 backend plus ProfitFab/Clarion with two users. This checklist already exists in session-vfs `MAINTENANCE.md`. |

**Can L2 test locking without a VM?** Partly. A Samba container with
`server min protocol = NT1` can act as an SMB1 backend fixture, and
two `smbclient` sessions against the proxy container can exercise
open/share-mode conflicts. Kernel CIFS mounts need a privileged
container on a host with the `cifs` module, which means a self-hosted
runner, not a GitHub-hosted one. The real Windows 2008 backend remains
L4 only.

## 4. Upgrading deployed appliances

### Principles

1. **Know the starting version** (M1). Every update reads
   `/etc/<appliance>.release` and refuses an unknown starting point.
2. **One update mechanism per appliance, not one per change.**
   Generalize the `inplace-0.4.0` pattern into a versioned bundle
   with the same steps every time: preflight refusal checks, backup to
   `/var/backups/<appliance>-update/<ts>`, ordered migrations
   (`migrations/NNN-*.sh`, each idempotent and recorded in `.release`),
   apply, verify, and print the rollback command.
3. **Production installs only what CI built and the lab qualified**
   (M3).
4. **OS packages follow a per-appliance policy:**
   - **Proxy**: Samba is held (H2). It moves only by the qualification
     path T-UPG-3, then a bundle carrying the matching VFS `.deb`.
     Other Debian security updates may flow normally.
   - **AD DC**: Debian security updates flow normally. Before
     deploying a new Samba minor version, run the lab release gate on
     it.
   - **Debian major version** (trixie → forky): never in place on a
     DC. Build a new image, join it as an extra DC, move roles, then
     demote the old DC (T-DC-3). For the proxy, a new image plus
     migration of share state. Trixie is supported until mid-2028, so
     this is planning only for now.

### Recommended direction: package the appliance runtime as `.deb`s

Ship each appliance's runtime (sconfig, helpers, generated-unit
templates, migrations) as a Debian package in the same signed APT
repository designed for the VFS:

- `smbproxy-appliance` depends on `smbproxy-session-vfs (= x.y)`,
  which depends on `samba (= exact)`. Apt then enforces the Samba pin
  without any hold, which fixes H2 structurally.
- Versioning, upgrade, and rollback (`apt install pkg=<old>`) become
  standard Debian operations. That also fits the "boring system
  administration" framing for operators in `CONTEXT.md`.
- `prepare-image.sh` shrinks to "install packages plus image hygiene".
  `postinst` runs the migrations.
- New components later become new packages instead of more code inside
  two 3,000-line scripts.

**Cost**: an L-size refactor. Bundled tarballs (principle 2) can
deliver the near-term upgrades first, and the packages can wrap the
same migration scripts later. Nothing is wasted.

### Owner direction (2026-10-08)

- **Units in the field**: one AD DC and one proxy. They keep the
  proven tarball method: one versioned bundle per transition, built
  the same way as `updates/inplace-0.4.0`.
- **Images built from now on**: ship with a built-in, standard update
  mechanism (release identity file, ordered migrations, backup,
  verify, rollback), so future fresh installs never need a hand-made
  tarball again. The first new image is also the first one able to
  receive updates this way.
- **Platform**: development and deployment are restricted to Windows
  hosts with Hyper-V on x86_64/amd64. Other hypervisors and arm64 stay
  documented as future work but are no longer tested or promised.
